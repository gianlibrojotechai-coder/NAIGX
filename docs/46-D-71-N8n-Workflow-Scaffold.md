## 1. What the owner asked, and what an honest answer is

"Build it in n8n directly" could mean two things. Building *into the owner's
n8n* is out: the standing constraint says n8n is untouched, and a workflow
half-configured by a machine inside a live instance is not a guide, it is a
mess someone else has to clean up. Building *a file n8n imports* is what
this record does, and it is exactly the shape of the request: the owner
builds it, with a guide, and the guide is on the canvas next to each node.

The honest boundary: NAIGX knows the node, its purpose, its setup and its
credential (D-70's `implementation` block) — as prose the model wrote. It
does not know field-level parameter values it never stated. So the file
places the nodes, wires them, and writes the guide; it does **not** set
parameters. The first sticky note says so, in the file itself.

## 2. The decision

**A third artifact on the job-description path, `n8n_workflow`, rendered
deterministically from the rank-1 project's `implementation` block when
that block's platform is n8n, and omitted with the reason otherwise.**

| Element | What it is |
|---|---|
| Shape | n8n's own import document: `name`, `nodes`, `connections`, `settings`, plus a `naigx` block (`standing: "scaffold"`, `steps_mapped`, `steps_unmapped`) so the stored document says what it is (`DP-1`) |
| README note | First on the canvas: the project's name, why it exists, the business problem, what to build, how to use the file, and the standing — *a scaffold generated by NAIGX, not a finished workflow* |
| One node per step | Type from a fixed name → type table (Webhook, Schedule Trigger, HTTP Request, IF, Switch, Set, Code, Merge, Split Out, Wait, Filter, HubSpot, Salesforce, Postgres, Airtable, Google Sheets, Gmail, Slack, Telegram, Notion, OpenAI, …), placed left to right; `notes` on the node carries its purpose |
| One note per node | Above it: the step's workflow line, why this node, the setup lines verbatim, the credential (or "none") |
| Wiring | Linear in step order. A trigger node starts a new chain: nothing is ever wired *into* a trigger |
| Unknown node name | A `No Operation` placeholder named `<node> (replace me)`, with a note that says NAIGX could not map it and what to do. The model's word is kept; nothing is silently mapped to something else |
| Wiring notes | A closing note with the implementation's `notes` (error workflow, retries, pinned data) |
| Parameters | Left at defaults, deliberately (§1) |

**Planning.** Written at Stage 9 when the portfolio exists — like the brief
at Stage 2 (D-66) — as a decision either way (`FR-091`): planned with a
reason when the first project is on n8n; omitted with the reason when the
project has no implementation block or is on another platform. Rendered on
Stage 9's own trace, so the stage keeps one trace (`AP-8`). Not in
`PATH_ARTIFACT_TYPES`, because Stage 8 cannot know whether the block will
exist.

**Presentation.** In the analysis view the artifact block shows the standing
banner (with how many steps mapped), a *Download for n8n* button producing
the file as stored, and the same step-by-step guide readable before
importing. The export lists the nodes in order and where to get the file;
the JSON itself is not printed into a PDF.

## 3. What is not claimed

- Not a finished workflow, and nowhere presented as one.
- Not verified against a running n8n by NAIGX. The document follows n8n's
  import format (nodes with `type`, `typeVersion`, `position`, `parameters`;
  `connections` keyed by node name; sticky notes as
  `n8n-nodes-base.stickyNote`) with deliberately old `typeVersion`s that
  current n8n still imports. The owner's first import is the real test, and
  a failure there is a defect to report against this record.
- Not a change to reasoning: the renderer adds no claim the implementation
  block did not make.
